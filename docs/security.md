# セキュリティ設計

## 1. 脅威と前提

- 公開された GAS Web アプリの URL は、知っていれば誰でも呼べる前提（Core は匿名アクセス）
- 共用 iPad は複数のスタッフが触る。ブラウザの端末トークンは複製可能な認証情報であり、物理的な iPad の完全な識別は保証できない
- 管理者の Google アカウントには Shiftly 以外のファイルがある（保護対象）
- Google Drive の所有者（管理者）による直接編集は技術的に防止できない（監査ログ・原本と修正の分離で検知性を高める）

## 2. 認証

| 主体 | 方式 | 実装 |
|---|---|---|
| 管理者 | Google 認証（Admin=アクセス自分のみ）→ Admin が HMAC-SHA256 で署名し Core へ転送（60 秒の時刻窓・ノンスでリプレイ防止） | src/gas/admin.ts, src/backend/auth.ts |
| Setup | 同上（role=setup）。許可操作は更新関連のみ（SETUP_ALLOWED_OPS） | auth.ts |
| 初期化（v1.3.0 A案。D-029） | Google 所有者がエディタで `shiftlyAuthorize` を実行、またはテスト用 URL（/dev）で `shiftlyWebInitialize`（操作するアカウント＝実行するアカウント・Setup の確認コードのハッシュ・未完了のときだけ・失敗回数の制限） | src/gas/core.ts |
| ペアリング | Admin / Setup が鍵を生成して送信前に保存し、ペアリングコード（Core は SHA-256 のみ保持）とともに登録。Core は鍵を再送しない。応答喪失時は保存済みの鍵での署名付き呼び出しで登録済みを確認。Admin の接続リセットは Core のエディタ実行（管理者本人）のみ | src/gas/core.ts, admin.ts, installer.ts |
| 店舗端末 | 管理者が発行した 10 文字・15 分・使い捨ての登録コード → 256bit 端末トークン（DB には SHA-256 のみ）。失効可能 | auth.ts |
| スタッフ（本人確認済み） | 端末トークン＋氏名選択＋個別 PIN（4〜12 桁）。セッションは発行端末に紐づき、絶対 30 分・無操作（既定 60 秒＋猶予）で失効 | auth.ts |
| スタッフ（本人未確認・v1.3） | PIN 未設定のスタッフは端末トークン＋氏名選択のみ。セッションに `verified=false` を記録し、権限を打刻・公開シフトに削る。`allowUnverified` の操作（打刻・公開シフト・承認待ちとなる申告）以外は `IDENTITY_REQUIRED` | auth.ts / api.ts |
| 管理者モード（v1.3） | 登録済み端末＋管理者パスワード（12 文字以上・3 種類以上の文字・推測されやすい語の禁止）→ 256bit 管理者トークン（DB には SHA-256 のみ、画面のメモリ上のみ保持）。発行端末に紐づき、無操作 5 分・絶対 4 時間・ログアウト・パスワード変更・端末失効・復元で失効 | auth.ts / handlers/admin-auth.ts |
| 機密操作 | 別の管理用パスコード（10 文字以上、英数字混在）による追加認証（5 分間） | auth.ts / api.ts |

- ブラウザ入力で owner/system を名乗ることはできない（`handleRequest` の trusted 引数はサーバー側でのみ指定）
- 管理者ログインの応答が、キャンセル・タブ非表示・画面の破棄の後に届いた場合は管理者モードにせず、そのセッションをサーバー側で失効させる（Codex 監査2 #9）
- 管理者モードの可否はブラウザ側の申告を信用せず、要求ごとにサーバーで管理者セッション（端末一致・失効・期限・無操作・パスワード変更後の無効化）を検証する。スタッフのセッショントークンは管理者トークンとして通らない（別テーブル・別のハッシュ接頭辞）
- 管理者モードで実行できるのは `staff_or_owner` と、`adminAllowed` を明示した `owner` の操作のみ（既定は不可）。Google 所有者に限定する操作（初期化・保守作業の開始と終了・Setup との接続のリセット・管理者パスワードの初期設定/再設定/ロック解除・PDF の端末への返却）は管理者モードから実行できない（全操作を走査するテストで確認）
- 重要操作（給与確定・訂正、権限変更、PIN・管理用パスコードの設定/解除、端末の登録/失効、給与規定の確認）は、管理者モードでは直近 5 分以内のパスワード再入力（`reauth`）が必要
- **アプリ内の復元・稼働中の DB の切替・自動更新・更新に伴う DB の移行・メンテナンスの切替は v1.3 では提供しない**（D-027）。処理を配布物から削除し、操作名は `DEFERRED_OPS` でどの経路（Google 所有者・定期処理・管理者モード・スタッフ・匿名・Setup の鍵）からも `NOT_IN_THIS_RELEASE` で拒否する（tests/security/deferred-features.test.ts）。Setup の鍵で実行できる操作は読み取りだけ
- データの復元は Google 所有者の保守作業（maintenance.begin / finish）。開始から終了まで、Google 所有者・定期処理を含む全員の更新系を止め（記録は Script Properties。記録を読み取れない場合も止める）、終了で守る記録の削除・変更、同じ ID の行の重複・行のシートの移動を検出したら再開しない。DB のセルに数式があれば再開しない。開始時の記録を確認できない場合は、今の DB を新しい基準にして開始し直さず、保守中のまま止める（所有者の確認だけで完全性を保証したことにしない。D-027 追補）。終了で全セッションを失効し、画面の世代を再発行する
- 管理者パスワードの初期設定・再設定は Google 所有者（Shiftly-Admin の署名付き要求）のみ。管理者本人の変更は現在のパスワードが必要。共通の初期パスワード・ハードコードされたパスワードはなく、未設定時は管理者ログインできない（認証を省略しない）
- Google 側の本人承認が必要な操作（GAS の構築・更新・権限承認）は、管理者パスワードでは迂回できない
- OAuth アクセストークンはサーバー（GAS）内でのみ使用し、ブラウザ・URL・ログ・DB に出さない

## 3. PIN・パスコードの保護

- 保存: `hash = PBKDF2-HMAC-SHA256(password = HMAC(pepper, PIN), salt[16B], 1000 回, 32B)`。平文は保存しない
- pepper（32 バイト乱数）は Core の Script Properties にのみ保存し、DB・バックアップに含めない → DB が漏えいしてもオフライン総当たりができない
- オンライン試行制限: 個人 5 回失敗でロック（基本 15 分・設定変更可）。v1.3: 短い PIN（4 桁）への総当たり対策として、ロックのたびにロック時間を倍にする（15→30→60 分…上限 24 時間。成功でリセット）。2 回以上の連続ロックは Google 所有者に通知。端末単位で 15 分 20 回、登録コードは全体で 15 分 100 回
- PIN の有無はサーバーの DB で判定する。PIN 設定済みのスタッフは PIN なし・空欄では認証されず（`PIN_REQUIRED`）、本人未確認ログインに切り替わらない。PIN 未設定のスタッフに PIN を送ると拒否（`PIN_NOT_SET`）し、未設定と誤入力を混同しない
- PIN 未設定のセッションは、その後 PIN が設定されても本人確認済みにならない（PIN の設定・解除でセッションを失効）
- 管理者パスワード: PIN と同じ方式（pepper 付き PBKDF2、反復 2,000 回）。5 回失敗でロック（基本 15 分・段階延長）、端末単位で 15 分 10 回、全体で 1 時間 30 回。ロック解除は Google 所有者
- 定数時間比較、PIN の形式制限（同一数字の繰り返し・連番を禁止）
- PIN・パスコードの設定/リセット/解除は管理者専用（スタッフ管理権限でも他人の PIN は変更不可）。管理者モードでは再認証が必要
- PIN 未設定のスタッフの本人確認: 給与・明細・勤怠詳細が必要な場合は、管理者が対面で本人を確認したうえで PIN を設定するか、管理者モードで内容を確認して伝える（共用 iPad の画面に表示したまま離れない）

## 4. 認可（docs/permission-matrix.md）

- 全 op にサーバー側の認可。UI の非表示に依存しない
- 権限は毎リクエスト DB から再読込 → 変更は既存セッションの次の操作から反映
- 自己操作の禁止: 自分の勤怠修正・給与条件・雇用条件・有給・給与確定/訂正・退職処理
- 個人給与の推定防止（Codex 監査1 #9 で強化）: `payroll_view_all` がない人件費分析では、スタッフ別・時間帯別の金額を返さない。月合計・予定・予測・予算消化率・超過判定は、閲覧者本人を除く人件費発生者が 3 名未満なら返さない。日別・曜日別は、金額のあるすべての区分で本人以外が 3 名以上の場合のみ返す（一部だけ伏せると合計との差分で推定できるため）
  - 残存リスク: 日をまたいだ合計の推移（昨日と今日の差分）など、複数回の閲覧の比較による推定は完全には防げない
- IDOR: 本人用 op は ID 引数を受け取らず、セッションの本人のみを対象。他人の明細はサーバーで本人性を確認
- v1.3 本人の勤怠修正・休憩申告・早出残業申請: 対象の勤務はサーバーが本人の打刻から特定する（勤務キーを指定しても本人の勤務に一致しなければ NOT_FOUND）。本人未確認の申告は承認待ち（未反映）で、応答に勤怠の詳細を含めない。確定済み期間の修正は承認待ち（給与の訂正フローで処理）
- 委任スタッフは、自分の早出残業申請・本人修正・休憩申告を承認できない（自己承認の禁止）

### 4.1 保守作業と古い画面（D-026・D-027）
- 全 API 操作に分類（kind）を型で必須にし、画面上のデータに基づく業務更新（edit）は API の共通の入口（ロックの内側）で、画面がデータを取得した時点の画面の世代を照合する。世代が古い・ない場合は STALE_VIEW、サーバーの世代の記録がない・壊れている場合は EPOCH_UNAVAILABLE で拒否する
- 世代は業務 DB・バックアップの外（Script Properties）にあり、DB の内容の変更で巻き戻らない。値は時刻に依存しない乱数で、発行は初めての構築と保守作業の終了だけ。既存の環境で記録が失われた・壊れた場合は自動で作り直さず、業務の更新を止める（Codex 監査24 A1）。照合しない更新系の操作（打刻・認証・システム・出力・内部処理）は操作ごとに理由を登録する（docs/permission-matrix.md）
- Shiftly-Admin は、ブラウザ由来のフィールドのうち op・args・requestId・epoch だけを署名して Core へ転送する

## 5. 入力検証・出力

- サーバー側で型・範囲・形式を検証（src/backend/validate.ts）。日付・時刻・金額・ID のパターンを限定
- CSV: `= + - @ TAB CR` で始まる文字列セルに `'` を付与（数式インジェクション対策）、UTF-8 BOM
- Sheets 書き込み: `valueInputOption=RAW`（数式評価させない）
- XLSX: inlineStr（文字列として格納）
- XSS: React のエスケープのみ（`dangerouslySetInnerHTML` 不使用。lint ルール・コードレビューで確認）。PDF 用 HTML は全値をエスケープ
- エラー応答に内部情報（スタック・個人情報）を含めない

## 6. 端末へのデータ保存

| データ | 保存先 |
|---|---|
| 端末トークン | localStorage（`shiftly.device.v1`）のみ |
| 勤怠・給与・シフト・個人情報・PIN・OAuth トークン | 保存しない（React state のみ） |

- ログアウト・打刻完了・無操作・タブ非表示・bfcache 復元でセッション終了と state 破棄
- HtmlService のレスポンスヘッダーは制御できないため、HTTP キャッシュ・ページ復元・PDF 表示の残存は完全には制御できない（meta の no-store、共用 iPad では明細を HTML 表示のみ・ダウンロード不可で軽減）。**iPad 実機での確認は未実施**
- キャッシュクリアで失われるのは端末トークンのみ（再登録で復旧。クラウドの業務データは失われない）

## 7. Google Drive の保護

- Core は drive.file（Shiftly が作成したファイルのみ）。フル drive・spreadsheets スコープは要求しない
- 削除はアプリ管理フォルダ配下のバックアップのみ（親フォルダを確認しゴミ箱へ。完全削除しない）
- スタッフへの Drive 共有はしない（共有 API を使用しない）

## 8. 監査ログ

- 権限変更・PIN 設定/解除・端末登録/失効・勤怠修正（本人修正・本人未確認を区別）・休憩申告・早出残業申請と確認・シフト外勤務の確認・給与確定/訂正・明細の他者閲覧・出力・バックアップ/復元・設定変更・認証失敗/ロック、管理者モードのログイン/再認証/ログアウト/パスワード変更・管理者モードでの全更新操作を記録
- 個人情報・秘密情報（PIN・トークン）は記録しない（テストで確認）

## 9. 残存リスク（受容・要対応）

| リスク | 内容 | 対応 |
|---|---|---|
| 乱数品質 | `Utilities.getUuid()` の乱数源の暗号学的品質は公式に明記なし | 複数 UUID を連結し SHA-256 で整形。要確認事項として記録 |
| 端末トークンの複製 | 同じトークンを別端末に複製できる | 失効→再登録の手順。最終利用日時で異常検知 |
| Setup ホスト型（A案で標準。D-029） | 開発者が公開する Setup のコードが、利用者の権限で動く（開発者を信頼する必要。開発者が Setup のコードを変えると、次に開いた利用者の権限で動く） | 共通 Setup の配置はリポジトリの main から作った配布物だけ（docs/deployment-guide.md「6」）。Setup は初回の構築だけで、構築済みの環境を変更しない（D-027）。業務データは利用者の Drive だけ。一般公開は OAuth 審査の後 |
| 共通 Setup の利用者の間の分離（D-029） | 複数の利用者が同じ Setup を使う | 記録・秘密情報は UserProperties（利用者ごと）と利用者の Drive だけ。Script Properties・Script Cache・Script Lock は使わない（テストで確認）。例外のログなし。**2 つのアカウントでの実環境の確認（L47）まで検証済みとしない** |
| ブラウザでの初期化（D-029） | Staff の公開 URL（匿名）から初期化を呼ばれる | 操作するアカウント＝実行するアカウント（匿名は空）＋確認コードのハッシュ＋未完了のときだけ＋失敗回数の制限。初期化の内容は shiftlyAuthorize と同じ（冪等）。確認コードは URL のフラグメントで渡し、ブラウザの履歴に残る（初期化の完了後は無効） |
| OAuth 未確認アプリ（D-029） | 審査前の共通 Setup は「Google で確認されていません」と表示される | 限定公開（テストユーザー）に限り、提供者が開発者本人であることを確認できる利用者にだけ案内する。一般公開は審査の後 |
| Drive 所有者の直接編集 | DB を直接編集できる | 原本・修正の分離、監査ログ、整合性チェック。完全防止はできない |
| Google アカウント喪失 | 同一アカウント内のバックアップでは不十分 | docs/operations-guide.md の別管理アカウントへの保護されたバックアップ手順（管理者の承認後に実施） |
| GAS 実行時の制約 | HTTP ヘッダー（CSP 等）を設定できない | React のエスケープ、外部スクリプトは Google Fonts の CSS のみ |
| PIN 未設定のなりすまし（v1.3） | 氏名選択だけで他人として出退勤・申告ができる | 本人未確認として記録し、修正・申請は承認待ち・管理者確認。給与・個人情報は非表示。PIN の設定を推奨 |
| 管理者パスワードの覗き見・共有 | 共用 iPad での入力を見られる・複数人で共有される | 入力は非表示・ブラウザに保存しない。無操作 5 分で終了。変更・再設定で全管理者セッションを失効。管理者の交代時は再設定 |
| 管理者パスワードのロックによる妨害 | 誤入力を繰り返すと管理者がしばらく入れない | Google 所有者の画面でロック解除・再設定。Shiftly-Admin（PC）からの管理は継続可能 |
| 管理者モードの idle 判定 | サーバーの無操作判定は CacheService に依存（消失時は失効側） | 画面側でも 5 分で終了。タブ非表示・再読み込みで終了 |
| 共用 iPad へのファイル保存 | 管理者モードでも出力ファイルは端末に返さないが、ブラウザの機能で画面を保存・印刷できる | 出力は Drive 保存のみ。アプリは端末に保存されたファイルを削除できないため、印刷・保存をしないよう運用で注意 |

## 10. 依存パッケージの脆弱性（npm audit, 2026-11-24）

- 本番に含まれる依存（`npm audit --omit=dev`）: **0 件**
- 開発用のみ: moderate 8 件（eslint / typescript-eslint が依存する minimatch の ReDoS: GHSA-g3hv-75wg-m249）。lint 実行時のみ使用され、配布物（GAS・HTML）には含まれない。修正は破壊的な版上げ（`npm audit fix --force`）が必要なため保留し、上流の修正版リリース後に更新する
