# 設計判断記録（ADR）

各判断は「背景 → 決定 → 代替案 → 影響」で記録する。ユーザー承認が必要なものは明記。

## D-001 対象リポジトリ
- 背景: 指示書の Repository は `chihirohashimotoac-coder/shiftly`。本セッションで操作権限があるのは `chihiro-hashimoto/shiftly`（Private・push 可）のみ
- 決定: `chihiro-hashimoto/shiftly` で作業。別リポジトリの新規作成・公開設定の変更はしていない
- 影響: 2026-11-24 ユーザーが `chihiro-hashimoto/shiftly` を正式な対象リポジトリとして確認（解決済み）

## D-002 セットアップ配信方式: GAS の Setup Web アプリ（GitHub Pages は不採用）
- 背景: GitHub Free の非公開リポジトリでは Pages を使えず、Pages は商用 SaaS・機密情報のやり取りに使用不可（official-sources §11）
- 決定: Setup を GAS Web アプリとして配布。2 方式: (A) 自己ホスト（管理者アカウントに Setup を 1 つ置く。clasp またはファイル貼り付け 1 回）、(B) ホスト型（配布者アカウントで「実行=アクセスしたユーザー」）
- 代替案: ローカル起動（Node が必要で管理者負担大）、Pages（不可）
- 影響: Apps Script API の呼び出しには Setup に紐づく**標準 Cloud プロジェクト**（無料）での API 有効化が必要（1 回のみ）

## D-003 Core を Shiftly-Staff に同居（共通バックエンド用 GAS は分けない）
- 背景: 更新経路の一本化が必須。Admin（アクセス=自分のみ）を Core にすると、匿名の Staff からのサーバー間呼び出しに drive スコープ付きトークンが必要になる
- 決定: Core（業務 DB の唯一の更新者）を匿名アクセスの Staff プロジェクトに置き、Admin は HMAC 署名で Core に転送
- 代替案: 3 プロジェクト（Core / Admin / Staff）→ 打刻ごとに UrlFetch が増え遅延増、承認工程も 3 回
- 影響: 公開エンドポイントは全操作で認証・認可（URL を知っていれば呼べる前提）。セキュリティテストで全 op を検査

## D-004 drive.file スコープ ＋ 高度なサービス（SpreadsheetApp は不使用）
- 背景: SpreadsheetApp.openById は `spreadsheets`（全スプレッドシート）スコープが必要。管理者の無関係なファイルの保護が必須
- 決定: Core は drive.file のみ。DB・フォルダは Core 自身が作成し、Sheets API v4 / Drive API v3 の高度なサービスで操作
- 影響: 【未検証】実環境での動作（docs/technical-verification.md §4）

## D-005 Admin・Setup と Core のペアリング
- 決定: Setup が生成したブートストラップ（Core: ペアリングコードの SHA-256 のみ、Admin: 使い捨てコード）で初回に HMAC 鍵を交換し、各プロジェクトの Script/User Properties に保存。Setup 鍵は更新関連の操作のみ許可（最小権限）
- 理由: 長期秘密をソースコードに埋め込まない。API で別プロジェクトの Script Properties は設定できない

## D-006 GAS の権限承認は管理者のエディタ実行（shiftlyAuthorize）
- 背景: API でのデプロイ成功と実行権限の承認は別。承認の自動化はできず、すべきでない
- 決定: Setup が該当工程で停止し、エディタを開くボタンと手順を表示。ping で完了を自動確認

## D-007 PIN 保護方式
- 決定: PBKDF2-HMAC-SHA256（反復 1,000、16 バイト salt）に、DB・バックアップと分離した pepper（Script Properties）を HMAC で結合。個人 5 回失敗で 15 分ロック、端末単位で 15 分 20 回の上限
- 理由: 6 桁 PIN はハッシュ単体ではオフライン総当たりに耐えないため、秘密鍵の分離とオンライン試行制限を主防御とする
- 未確認: GAS 上の PBKDF2 実行時間（反復回数は実測後に調整）

## D-008 金額計算は BigInt 有理数、端数処理は項目合計で 1 回
- 理由: 浮動小数点誤差の排除。日々の切捨て禁止（official-sources §16）。30 分単位の丸めは行わない（常に分・秒単位で計算）

## D-009 未対応の制度・未設定条件は確定禁止（フォールバックしない）
- 変形労働時間制等、標準報酬日額方式、出来高払の割増算定、期間途中の日割（規定未確認）は blocking

## D-010 XLSX は自前実装（SheetJS 等を導入しない）
- 理由: GAS・ブラウザ両対応、依存ライブラリのサプライチェーン・ライセンスリスク回避。openpyxl で読めることをテストで確認

## D-011 プレビューはモックデータのブラウザ内実行 ＋ CI Artifacts
- 背景: 非公開リポジトリのため無料・安全な公開ホスティングがない（Pages 不可）
- 決定: `npm run build:preview` の成果物（dist/preview）を GitHub Actions の Artifacts（リポジトリ権限者のみ）として保存。ローカルでは `npm run preview`

## D-012 共用 iPad での給与明細は HTML 表示のみ
- 理由: PDF のダウンロード・ブラウザキャッシュによる残存を避ける。PDF は管理者端末（payslips.pdf は管理者専用）

## D-013 依存パッケージの版
- 公開後 2 週間以上経過した版に固定（package.json は完全一致指定）。npm の arborist 不具合回避のため `.npmrc` に legacy-peer-deps（ピア依存は手動確認済み）
- TypeScript は typescript-eslint の対応範囲（<6.1）に合わせ 6.0.2

## D-014 名称変更（Kiosk→Staff、店長→管理者）と互換の旧識別子（v1.3）
- 背景: v1.3 で画面・文書・コード・GAS プロジェクト名の用語を統一。ただし単純な一括置換で既存環境・更新・ロールバックを壊さないこと
- 決定: 画面・文書・コードの識別子・ファイル名・ビルド成果物・新規 GAS プロジェクト名（Shiftly-Staff）を変更。次の旧識別子は互換のために内部に限って残す
  - GAS 関数 `kioskApi`（`staffApi` の別名）と API 操作 `kiosk.bootstrap`（`staff.bootstrap` と同じ）: 更新前から開いていた店舗端末の画面（旧 HTML）が更新後も動作するため
  - 打刻原本の `source: 'kiosk'`: 保存済みデータの値（画面では「店舗端末」と表示）
  - 既存環境の GAS プロジェクト名（Shiftly-Kiosk のまま）: Setup は保存済みの scriptId で識別するため、名称の変更は不要。新規作成分のみ Shiftly-Staff。作成中断からの再開時は前回の名称で案内
  - 過去の監査・レビュー記録（docs/reviews/, docs/review-log.md の過去分）: 記録の改変を避けるため原文のまま
- 端末登録の `kiosk.enroll` は公開操作を増やさないため互換名を残さない（`staff.enroll` のみ）
- 影響: 旧名の互換は次のメジャー更新で削除を検討

## D-015 1 台の iPad での管理者モード（管理者パスワード）（v1.3）
- 背景: 店舗用端末と管理者用端末を分けない運用。既存の管理者認証は Google 所有者限定の Admin と HMAC 署名が前提
- 決定: Core（Shiftly-Staff）に管理者パスワードの認証と管理者セッション（admin_credentials / admin_sessions）を追加。principal=admin は staff_or_owner と、`adminAllowed` を明示した owner 操作のみ実行でき、重要操作は `reauth`（5 分）。管理者パスワードの設定・再設定は Google 所有者のみ
- 代替案: (1) iPad で Google にログイン → 共用端末に Google のログイン状態・個人ファイルへのアクセスが残る、(2) スタッフの委任権限＋管理用パスコード → スタッフのセッションから管理者権限を得る経路になる
- 影響: 管理者モードは Google 所有者に限定する操作（構築・更新・復旧・管理者パスワード再設定）を行えない。**バックアップからの復元（F26）も復旧に含め、Google 所有者に限定する**（2026-11-26 ユーザーの判断。Codex 監査18 #2）。出力ファイルは共用端末に返さない

## D-016 PIN の任意化と本人未確認セッション（v1.3）
- 決定: PIN 未設定のスタッフは氏名選択のみで「本人未確認」セッション。権限を打刻・公開シフトに削り、`allowUnverified` の操作のみ許可。申告（勤怠修正・休憩・早出残業）は承認待ち
- 画面は氏名選択時に PIN なしでログインを試し、`PIN_REQUIRED` の場合のみ PIN を入力する（起動時のスタッフ一覧に PIN の有無を含めない）。PIN を照合していない試行は失敗回数に数えない
- PIN は 4〜12 桁。短い PIN の総当たり対策としてロック時間を段階的に延長
- 例外: 退勤打刻と同じ処理で受け付けた「予定どおり休憩を取得」だけは通常の退勤操作のため本人未確認でも反映（本人未確認として記録し、給与確定時に確認項目として表示）。事後の申告は本人未確認ならすべて承認待ち（Codex 監査2 #8）

## D-021 版番号と既存環境の更新（v1.3。Codex 監査2 #1〜#3）
- 決定: アプリの版を 0.2.0 とし（v1.2 は 0.1.0）、Setup の更新検出で既存環境に更新を提示する。Sheets は列幅（グリッド）を超える範囲を読み書きできないため、読み取りはシートの列数に制限し、書き込み前・移行時に列とヘッダーを拡張する
- 更新の失敗時は、コードを戻した後にプログラムと DB のスキーマの一致を確認してからメンテナンスを解除する（不一致なら継続し、更新前バックアップの復元を案内）。Core でも不一致の間はメンテナンスを解除しない

## D-017 休憩: 予定休憩は取得を確認したものだけ控除（v1.3。Codex 監査1 #8 への対応）
- 背景: v1.2 はシフトの固定休憩を「打刻休憩がない勤務」に自動適用しており、未取得の休憩を控除しうる（Codex 監査1 #8）
- 決定: `buildSessions` に休憩申告（break_declarations）を渡す方式に変更。予定休憩は「予定どおり取得（as_scheduled）」と申告・確認された勤務にだけ控除する。申告がない勤務は控除せず、給与確定時の確認項目にする。申告は勤務ごとの最新の反映済みのものを使い、短縮・延長・時間帯違い・追加は申告の区間（打刻休憩より優先）。打刻休憩がある勤務に予定休憩を重ねない（二重控除防止）
- 既存テスト（tests/unit/attendance.test.ts「固定休憩と打刻休憩を二重控除しない」）は変更していない。休憩申告を渡さない場合の純粋関数としての v1.2 の動作の確認として残し、製品のコード（services.sessionsFor）は必ず休憩申告を渡す
- 影響: シフトの `applyFixedBreak` 列は「予定休憩の時刻を指定した」ことを表す互換の列となり、控除の可否には使わない

## D-018 シフト基準の給与計算（v1.3）
- 決定: 店舗設定 `payrollTimeBasis`（既定 shift）。給与計算に渡す勤務を「(修正後の勤怠 ∩ 公開シフト ∪ 実労働と確認したシフト外) − 休憩」に変換する（打刻原本・修正後の勤怠は変更しない）。シフト外の時間は早出・残業・シフト間・シフト未登録に分類し、未確認の時間があれば給与確定を止める（blocking）
- 確認の解決: 実労働（承認・一部承認・管理者確認の区間の和集合）、実労働なし（明示的に「実労働なし」と確認した区間のみ）。一部承認の残りは、別に実労働なしと確認しない限り未確認（Codex 監査2 #6）。申請中・差戻し・取消・却下（実労働未確認）は未確認のまま。未確認の判定は秒単位、期間前の勤務の未確認も確定を止める（Codex 監査2 #4・#5）
- 理由: 申請・承認の有無で実労働を無給にしないこと、未確認のまま機械的にシフト時間で確定しないこと、同じ時間の重複加算をしないことを同時に満たすため
- 代替案: 打刻差分を自動で加算／自動で切り捨て → いずれも実労働の実態と乖離しうる
- 影響: v1.2 の給与テストは「実績どおり」を前提とするため、テストハーネスの既定を `actual` とし（前提条件の明示）、シフト基準は v1.3 のテストで検証。遅刻・早退は実際の勤務時間で計算（v1.2 と同じ）

## D-019 申請・確認データと復元（v1.3）
- 決定: 早出・残業申請は overtime_requests（現在の状態）＋ overtime_request_history（追記専用の履歴）。勤怠修正は既存の attendance_corrections に確認状態の列を追加（原本は不変）。休憩申告は break_declarations（追記し、置換は superseded）
- 復元時は、管理者パスワード・勤怠修正（確認状態）・休憩申告・早出残業申請を現行の状態で引き継ぐ（承認済みの実労働が復元で失われ賃金が変わることを防ぐ）。スキーマ v1 のバックアップは候補を v2 に移行してから整合性を確認

## D-020 Codex 監査の累計回数の引き継ぎ
- 決定: 新規セッションへの移行で監査回数をリセットしない。v1.3 実装後の監査は累計 2 回目として実施し、対象のコミット SHA を記録する（docs/review-log.md）

## D-022 復元・旧版への巻き戻しで保証する範囲（v1.3、Codex 監査8・9）
- 決定 1（復元と給与）: v1.3 の Core の復元は、給与の確定データ（給与期間・計算結果のリビジョン・明細）を現行から引き継ぐ。確定済みの給与がある期間はすべて（C-10 で、バックアップ後の変更の有無で絞る方式から変更。給与条件だけが異なる場合を検出できないため）、確定・訂正・明細の発行を停止し、管理者が時給ルール・手当・控除（月給制のスタッフがいれば月給設定も）の一致を確認した後に解除する（`payroll.releaseRestoreLock`、再認証・監査ログあり。監査ログには定型の確認項目と人数だけを記録し、自由記述は受け付けない）。解除の前に、確定済みの総支給額と現在の条件で計算し直した額を比べ（`payroll.restoreLockReview`）、解除の時点でサーバーが計算し直して差がない場合だけ解除できる（C-17 #1 で差額の確認を求めたが、確認が比較の内容と結び付かないため、C-18 #1 で差がない場合だけに変更）。停止の情報は system_metadata の `payrollRestoreLocks`（スキーマは変更しない）
- 決定 2（旧版への巻き戻し）: DB の移行後に旧版（v1.2）へ戻す運用は、緊急時に打刻を続けるための手段とし、**給与計算には非対応**とする。影響期間の給与は旧版で確定せず、紙のタイムカードとの並行記録と、Drive に残る v1.3 の旧 DB（`Shiftly Database (replaced 日時)`）から、v1.3 へ再更新した後に計算する。再更新後は、旧 DB の確定結果との照合（旧 DB で確定済みのものは再確定しない）・未確定分の再登録・別計算との照合を経て確定し、照合できない場合はシステム外で確定する（docs/update-rollback.md ⑨〜⑬）
- 理由: v1.2 のコードは変更できず、v1.3 の記録（休憩の申告・シフト外の実労働の確認など）を正しく扱えない。手順の追加では完全な保全を保証できないため、保証範囲を明示して運用で守る（ユーザーの判断、2026-11-25）
- 代替案: 復元で給与条件も引き継ぐ → 復元で給与条件を戻せなくなるため不採用（ユーザーの判断）。v1.2 の修正版を配布する → 既存の v1.2 環境の更新経路が増え、v1.3 への更新と同等の検証が必要になるため不採用
- 影響: 旧版での誤確定はシステムでは止められない（運用で守る）。実環境での検証（L1〜L17）で、更新・巻き戻し・復元・再更新の通しの確認が必要

## D-023 ロールバックの戻し先は版の組の記録から選ぶ（v1.3、Codex 監査13）
- 決定: Setup は、正常に稼働した Staff・Admin の版の組の履歴（Registry の `pairs`。更新の成功時に追加、最大 10 件）と、更新中に今回配備した版の組（`update.deployed`）を記録する。手動ロールバックは、更新を取り消し終えていなければ更新の開始時の組、それ以外は履歴の一つ前の組へ戻し、履歴をその組まで切り詰める。戻し先を確定できない・配備を照会できない場合は、メンテナンスを開始せずに中止する。更新の再開・完了は、実際の配備が今回配備した組と完全に一致する場合だけ配備を省略・完了する
- 理由: C-10〜C-13 で、各プロジェクトの「直前の版」と状態のフラグから組を推測する方式に、修正のたびに別の組み合わせで回帰が見つかった（版の組の推測が原因）。組を明示的に記録すれば、戻し先・完了の判定を完全一致で行える（ユーザーの判断、2026-11-25）
- 旧形式の記録（履歴がない）: 更新の記録があれば開始時の組だけ、なければ両方の「直前の版」の組と現在の組だけを確定できる組として扱い、それより前へは戻さない。今回配備した組の記録がない更新の記録は、両方の配備を終えた後の段階（移行・完了・承認待ち、移行済み）の場合だけ、Setup が最後に配備した版の組で代用する
- 補足（C-14）: 旧形式の記録で今回配備した組を代用するのは、Staff・Admin の両方が開始時の版と異なる場合だけ。履歴がない登録は、最初の更新の記録を作る前に確定できる組を履歴に保存する。前の組へ戻す手動ロールバックは、メンテナンスの開始を確認した後、最初の切替の直前に戻し先の組（`pendingRollback`）を保存し、両方の切替と照合を終えるまで保持する（その間は更新を始めない。C-15 で保存の時点を修正）
- 影響: `previousVersionNumber` は互換のために残すが、判定には使わない（旧形式の登録から履歴を作るときだけ使う）

## D-024 公開前（利用者なし）の扱いと「迷ったら止める」（v1.3、2026-11-26）
- 前提（ユーザー確認）: Shiftly はまだ公開しておらず、利用している店舗はない。v1.3 が最初に導入する版になる
- 決定 1: v1.2 で運用中の店舗を前提とした対応（v1.2 からの更新、v1.2 への巻き戻し＝D-022、v1.2 の Core での復元、旧形式の記録の扱い）は、現時点では該当なしとする。コードと手順は記録として残し、削除しない
- 決定 2: 更新・ロールバックの仕組みは、v1.3 の公開後に次の版を出す前に、Google の実環境で検証してから使う（モックでは検証できない範囲があるため）
- 決定 3（迷ったら止める）: Setup の更新・ロールバックで処理しきれない失敗が起きた場合は、それ以上の切替・解除をせずに中止し、メンテナンスを開始していた場合は解除しない。現在の配備の組とメンテナンスの状態を、確認できる範囲で返す（Installer.failSafe）。メンテナンスを解除するのは、Staff・Admin の版の組がそろい、DB の構造が一致すると確認できた場合だけ
- 理由: C-10〜C-16 で、更新・ロールバックの手順の間の失敗の余地を一つずつ塞ぐたびに、塞ぎ方が別の余地を生んだ（多段の処理をまとめて取り消す仕組みがないため、どの順番でも段の間の失敗が残る）。個別の対処をやめ、安全側に止める一つの規則で扱う（ユーザーの判断）
- 影響: まれな失敗で打刻が止まることがある。その間は紙のタイムカードで記録する（docs/operations-guide.md）

## D-025 ループを止めるための進め方と、復元・初回の構築の不変条件（v1.3、2026-11-26、Codex 監査19 の分析）
- 背景: C-6〜C-19 で、修正のたびに隣の条件で新しい指摘が見つかった。分類すると、(A) 復元の意味づけ（C-6#2・C-8#1・C-9#1・C-10 回帰2・C-17#1#2・C-18#1#2・C-19#1）、(B) 更新・ロールバックの多段処理（D-023・D-024 で対応し、実環境での検証に回した）、(C) 初回の構築での外部の作成の一回性（C-1#12・C-17#3・C-19#2）、(D) v1.2 の手順（該当なし）。ループしていたのは A と C
- 根本原因: ①指摘の再現条件だけを直し、守るべき不変条件の全体を直していなかった（例: 比べる項目を総支給額→月給→控除と一つずつ足した。引き継ぐ表を一つずつ足した）②テストが指摘の再現だけで、対象の全体（全表・全項目・全失敗の種類）を検証していなかった ③Codex に渡す前に、隣の条件を自分で点検していなかった
- 進め方（以後の修正の規則）: 指摘ごとに「守るべき不変条件」を書き、それを破り得る経路を全体から洗い出して直す。テストは対象の全体を列挙して検証する（表・項目・失敗の種類の一覧をテストで回す）。Codex に渡す前に、結論を伝えない独立した点検を行う
- 決定 1（復元。不変条件 R1）: 全表の扱いを `RESTORE_POLICY`（src/backend/handlers/ops.ts）で明示し、型で全表の指定を必須にする。業務の入力・設定はバックアップの時点に戻し（restore）、起きた事実・履歴は再投入し（append）、認証・端末・申請と確認・給与の確定データ・バックアップの履歴は現行を引き継ぎ（carry）、セッションは失効させる（revoke）。この分析で、端末登録コード（使用済みのコードが再び使えた）・有給の付与と取得・シフトの変更履歴・出力の履歴・冪等性キーを巻き戻していたことが分かり、carry / append に改めた。復元で行の**版を小さくしない**（引き継いだ行は復元前・候補のどちらの版よりも大きく、戻した行はバックアップの後に更新されていれば復元前の版 + 1。復元前に開いていた画面からの古い内容の上書きを、版の照合で拒否する。独立した点検 R1-1）。復元後の給与の停止の記録を読み取れない場合は、停止なしと見なさずに止める
- 決定 2（復元後の給与。不変条件 R2）: 確定済みの給与がある期間の停止は、解除の時点でサーバーが計算し直した結果が、確定済みの結果と**計算結果の全項目**（日数・時間・支給の各項目・手当・控除の内訳・差引支給額）で一致し、確定を止める問題もない場合だけ解除できる（`differingTotals`）。項目を個別に選んで比べない。制約: 計算の版（法令ルールセット・計算方法）が確定時と変わった場合は差が出て解除できない（次の版を出す前に、計算の変更と復元の扱いを決める）
- 決定 3（初回の構築。不変条件 S1）: 外部の作成の要求の失敗は、Google が拒否したこと（4xx）が分かる場合だけ「作成されていない」とする。それ以外（通信の例外・タイムアウト・5xx・応答の喪失）は「作成されたか分からない」として最初の失敗から確認を案内し、確認の明示（画面のチェック。サーバー側で検証）があるまで作成の目印を外さない。デプロイは説明で一覧と照合する。記録する版は、実際のデプロイの版を応答または照会で確かめてから保存する（確かめられなければ止める）。Drive 上の作成物（Core の初期化でのフォルダ・DB、Setup の記録ファイル）は、既存を探す検索・内容の取得に失敗した場合に「存在しない」と見なさず、作らずに止める（再実行で既存を見つけて使う）。デプロイの作成も同じ規則で扱い、結果が分からない場合は一覧で説明を照合し、一覧に現れなければ（反映の遅れがあり得るため）確認の明示があるまで作らず、確認の後も同じ説明で作成する。成功の応答に作成したものの ID がない場合も「結果が分からない」として扱う。Setup の記録ファイルは、作成・使用したファイルの ID で更新し、複数ある場合は同じ環境なら最後に保存した記録を使い、別々の環境を指す場合は止める（独立した点検 S1-1〜S1-3）
- 独立した点検（2026-11-26、読み取りのみのサブエージェント。結論を伝えずに R1〜R3・S1・S2 の観点だけを渡した）: R2・R3・S2 は違反なし。R1 で 1 件（版の巻き戻り）、S1 で 3 件（デプロイの一覧 0 件での作り直し・ID のない成功応答・記録ファイルの重複）、低 3 件（復元の確認画面の説明・停止の記録の破損・ペアリングの確認の案内）を指摘され、すべて修正した（docs/review-log.md C-19）
