# 障害発生時の対応手順（v1.3.0）

> 対象: 店舗の管理者・Google 所有者・開発者。v1.3 は「正常時は自動・異常時は手動」です（D-027）。アプリ内の自動復元・自動復旧はありません。
> **この文書の手順のうち、Google 実環境で確認していないものは「未検証」と書いています。未検証の手順は、検証（docs/live-verification.md）が終わるまで「利用できる」とは扱いません。** 本番の店舗の実データを登録する前に、L24・L25・L26 を終えてください。

## 0. 連絡先（店舗で記入する）

| 項目 | 内容 |
|---|---|
| 開発者の氏名・連絡手段（電話・メール・チャット） | （**未記入**。導入時に店舗で記入） |
| 連絡できる時間帯 | （**未記入**） |
| Google 所有者（Shiftly を構築したアカウントの持ち主） | （**未記入**） |

開発者に送る情報: 発生した日時、画面のメッセージの全文（スクリーンショット）、操作していた画面、Shiftly-Staff のエディタの「実行数」のエラーの内容。**パスワード・PIN・認証コード・スタッフの個人情報・給与の金額は送らない**（必要な場合は開発者から別の手段で依頼します）。

## 1. 最初にすること（共通）

1. 打刻できない・データがおかしい場合は、**すぐに紙のタイムカードに切り替える**（「2」）
2. 画面のメッセージを記録する（スクリーンショット）
3. **データを手で直さない・ファイルを消さない・作り直さない**（原因が分かるまで、Google ドライブの `Shiftly` フォルダとスプレッドシートを編集しない）
4. 開発者に連絡する（「0」）

| 症状 | 対応 |
|---|---|
| 店舗 iPad が「オフライン」・通信できない | 紙のタイムカード（「2」）。通信が戻れば再開 |
| 「保守作業中です」と表示される | Google 所有者が保守作業中。紙のタイムカード。終了を待つ |
| 「画面を読み込み直してください」 | 画面を読み込み直す（保守作業の後の正常な動作） |
| 「画面の世代の記録を確認できないため、データの更新を停止しています」 | 紙のタイムカード。Google 所有者が保守作業（開始 → 終了）を行う（docs/operations-guide.md「9」） |
| 「端末が登録されていません」（キャッシュの削除・Safari のデータの削除の後など） | 管理画面「店舗端末」で登録コードを発行して登録し直す。業務データは Google ドライブの DB にあり、端末の登録をやり直しても消えない（live-verification.md L27 で確認） |
| データが消えた・おかしい | 「3」（データの確認）→ 必要なら保守作業 |
| DB のスプレッドシートが開けない・見つからない | 「5」（DB のファイルの消失） |

## 2. 打刻できない間の紙のタイムカード

- 記録する項目: 氏名、日付、出勤の時刻、退勤の時刻、休憩の開始・終了（取った場合）、早出・残業の理由（シフト外の場合）、本人の署名、管理者の確認
- 紙の記録は、Shiftly に登録した後も、給与の確定まで（できれば法令の保存期間に合わせて）保管する
- 再開後、管理画面「勤怠」→「紙のタイムカードから登録」で、理由（例「障害のため紙で記録」）を付けて登録する。登録の内容は修正の履歴に残る

## 3. データの確認とバックアップ

- 管理画面「バックアップ」で、最新のバックアップの日時と状態（成功）を確認する。必要なら「今すぐバックアップ」で手動のバックアップを作る（業務の DB の複製が Google ドライブの `Shiftly/05_Backup` に作られる）
- バックアップの複製（`Shiftly_backup_…` のスプレッドシート）は、**閲覧だけ**にする（編集しない・移動しない・名前を変えない）
- データを戻す必要がある場合は、Google 所有者の保守作業（docs/operations-guide.md「9. 保守作業」の 12 手順）による

## 4. 保守作業・停止中の給与

- 保守作業の開始・終了: docs/operations-guide.md「9」（`shiftlyMaintenanceBegin` → 手で直す → `shiftlyMaintenanceFinish`）
- 保守作業の後、確定済みの給与の期間が停止したままの場合の例外的な手動訂正: docs/operations-guide.md「9.1」
- 開始時の記録・保守の記録を失った場合: docs/operations-guide.md「9.2」（保守中のまま。紙のタイムカードと開発者への個別の依頼）

## 5. DB のファイル（スプレッドシート）を失った場合の個別対応手順（開発者と Google 所有者）

> v1.3.0 のアプリの機能ではありません。**手順 5.2（ゴミ箱からの復元）と 5.4（バックアップからの記録の取り出し）は L25 で確認するまで未検証、手順 5.5（環境の作り直し）は v1.3.0 では検証済みの手順がありません**。未検証の復旧の能力は保証しません。

### 5.1 状況の確認（Google 所有者）
1. 店舗は紙のタイムカードに切り替える（「2」）
2. Google ドライブで `Shiftly/01_Database` を開き、`Shiftly Database - （店舗名）` があるか確認する。ない場合は Google ドライブの検索で名前を検索する（別のフォルダに移動していないか）
3. 移動していた場合は、**元の `01_Database` フォルダに戻す**（ファイルの ID は変わらないため、アプリはそのまま使える。戻した後は 5.3）

### 5.2 ゴミ箱にある場合（もっとも多い想定。未検証）
1. Google ドライブの「ゴミ箱」を開き、`Shiftly Database - （店舗名）`（`Shiftly` フォルダごと削除した場合は `Shiftly` フォルダ）を選び「復元」
2. ゴミ箱から戻したファイルは ID が変わらないため、アプリは同じファイルを使う。5.3 に進む
- 注意: Google ドライブのゴミ箱のファイルは一定期間の後に自動で削除されます（期間は Google のヘルプで確認。要確認）

### 5.3 戻した後の確認（Google 所有者）
1. Shiftly-Staff のエディタで `shiftlyMaintenanceBegin` を実行（業務を止め、開始時のバックアップを作る）。失敗した場合は開発者に連絡（保守中のまま）
2. 管理画面で、スタッフ・直近の打刻・給与の確定の状態を確認する。紙のタイムカードの記録があれば、保守の終了の後に登録する
3. `shiftlyMaintenanceFinish` で再開（整合性の確認・全員のログインの解除）。問題があれば再開しないので、実行ログの内容を開発者に送る

### 5.4 完全に削除された場合: バックアップからの記録の取り出し（未検証。L25）
1. Google のヘルプ（Google ドライブの「ファイルを探す・復元する」）で、完全に削除したファイルを復元できるか確認する（できる場合・期間・方法は Google の扱いによる。**要確認**。推測で他のファイルを差し替えない）
2. 復元できない場合は、`Shiftly/05_Backup` の**最新の**バックアップ（`Shiftly_backup_daily_…`・`Shiftly_backup_manual_…` など。名前の日時が作成の日時）を開く（閲覧だけ）
3. 「ファイル」→「ダウンロード」→「Microsoft Excel（.xlsx）」で保存し、**アクセスを制限した場所**（Google 所有者・管理者だけが見られる場所）に保管する。各シートの意味は docs/database-schema.md（例: `employees` スタッフ、`attendance_events__YYYY_MM` 打刻原本、`attendance_corrections` 修正の履歴、`shifts` シフト、`payroll_results` 確定給与、`pay_slips` 明細）
4. バックアップの作成の日時より後の記録（打刻・修正・申請・給与の確定）は、バックアップにありません。その分は紙のタイムカード・管理者の記録で補う
5. 進行中の給与期間は、バックアップの記録と紙のタイムカードから、**従来の方法で計算**して支払う（法令・就業規則の支払期日を守る。記録は docs/operations-guide.md「9.1」の項目に準じて残す）

### 5.5 環境の作り直し（開発者の個別の判断。v1.3.0 では検証済みの手順なし）
- 稼働中の DB をバックアップの複製に切り替える（Script Properties の DB の ID を書き換える）操作は、v1.3 で延期した「稼働中の DB の切替」にあたるため**行いません**
- 環境を作り直す場合は、開発者が個別に方法を判断し、検証用の環境で確認してから行います（新しい環境の構築・スタッフや給与条件の再登録・過去の記録はバックアップのファイルを閲覧用の記録として保管、などが候補。**未検証**）
- 作り直すまでの間は、紙のタイムカードと従来の給与計算で運用します

## 6. 優先度（公開後の不具合）

| 優先度 | 内容 | 対応 |
|---|---|---|
| P0 | データの消失・個人情報の漏えい・権限の不正な利用・重大な給与の誤り | 利用を止める（紙・従来の計算）→ 影響の確認 → 最優先で修正 |
| P1 | 打刻できない・給与を計算できない・初回の構築ができない・主要な機能の不具合 | 速やかに修正 |
| P2 | 操作性・速度・見やすさ・軽微な不便 | 利用状況に応じて改善 |
| P3 | デザイン・便利な機能・保守の自動化 | 必要に応じて |

修正は別のブランチ・別の PR で行い、ユーザーの承認の後に main へ反映し、docs/update-rollback.md「2」の手順で環境に反映します。
