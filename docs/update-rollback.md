# アップデート・ロールバック（v1.3: 自動では行わない）

> **v1.3 の範囲（2026-11-27、B案。docs/decisions.md D-027）**: アプリの自動更新（アプリ内・Shiftly Setup・定期処理）、更新に伴う DB の自動移行、自動ロールバックは **v1.3 では提供しません**（次期以降の候補。実施は約束しません）。
> 処理は配布物に含めず、どの経路から呼ばれてもサーバーが `NOT_IN_THIS_RELEASE` で拒否します（tests/security/deferred-features.test.ts）。
> 以前の版の設計・手順（Setup の「アップデート」「直前のバージョンに戻す」、版の組の記録、更新前バックアップ、v1.2 からの更新・巻き戻し）は、git の履歴（コミット b8ab444 までのこの文書）に開発資産として残しています。v1.3 の運用では使いません。

## 1. v1.3 で行うこと・行わないこと

| 項目 | v1.3 | 備考 |
|---|---|---|
| 初回の構築（コードの配置・版の作成・Web アプリのデプロイ・DB 構造の生成） | **自動**（Shiftly Setup） | docs/installer-guide.md |
| 構築済みの環境のアプリの更新 | **行わない**（自動更新なし） | Setup は、構築に使った版と異なる版では既存の環境を変更しない。Setup の画面に更新のボタンはない |
| 更新に伴う DB の自動移行 | **行わない** | `system.migrate` は拒否。初回の DB 構造の生成（F01）は別 |
| 自動ロールバック・未知の障害の自動復旧 | **行わない** | 障害時は保守作業（docs/operations-guide.md「9. 保守作業」） |
| アプリ内のデータの復元・稼働中の DB の切替 | **行わない** | データの復元は Google 所有者の保守作業 |
| メンテナンスの手動の切替（`system.setMaintenance`） | **行わない** | 業務の停止・再開は保守作業の開始・終了（maintenance.begin / finish）だけ |

## 2. 公開後の手動アップデート（v1.3.0 から。Google 所有者の保守作業）

v1.3.0 の公開後に修正版（v1.3.1 など）を反映する手順です。自動更新は行いません（実装もしません）。**この手順は Google 実環境では未検証です。最初の修正版を配布する前に、検証用の環境で一度この手順を実施して確認します（live-verification.md の L31）。確認するまでは、本番の環境に修正版を反映しません。**

### 2.1 反映してよい修正版の条件（開発者が配布の前に確認する）

| 条件 | 確認の方法 |
|---|---|
| DB の構造（スキーマの版）が変わらない | 修正版の `SCHEMA_VERSION`（src/backend/schema.ts）が現在の環境と同じ。変わる修正版は、この手順では反映できない（更新に伴う DB の移行は延期した機能。D-027）。必要になった場合は、その版の公開前に別の手順を用意して検証する |
| Staff（Core）と Admin を同じ版の配布物から反映する | GitHub Release の同じ `shiftly-gas-bundle.zip` の `core/` と `admin/` を使う（版の混在で使わない） |
| 権限（appsscript.json の oauthScopes）の変更の有無 | 変わる場合は、反映の後に各エディタで `shiftlyAuthorize` を実行して承認し直す |
| CI の成功・リリースノート | 修正版の GitHub Release に、変更内容・影響範囲・この手順で反映できること・失敗時の扱いを書く |

### 2.2 手順

| # | 作業 | 方法 |
|---|---|---|
| 1 | 店舗への連絡 | 作業の時間帯と、作業中は打刻できない（紙のタイムカード）ことを伝える |
| 2 | 更新前の版の確認 | 管理画面「システム・保守」（または Shiftly-Staff のエディタで `shiftlyMaintenanceStatus`）で、コードの版（codeVersion）・DB のスキーマの版を記録する |
| 3 | 業務の停止とバックアップ | Shiftly-Staff のエディタで `shiftlyMaintenanceBegin`（全員の更新を止め、開始時のバックアップを作る。docs/operations-guide.md「9」） |
| 4 | 更新前のデプロイの版の記録 | Shiftly-Staff・Shiftly-Admin それぞれで「デプロイ」→「デプロイを管理」→ Web アプリのデプロイの「バージョン」の番号を記録する（戻すときに使う） |
| 5 | Staff（Core）のコードの反映 | Shiftly-Staff のエディタで、`Code.gs`・`staff`（HTML）・`appsscript.json` の中身を、修正版の `core/Code.js`・`core/staff.html`・`core/appsscript.json` で置き換えて保存する（ファイルを追加・削除しない） |
| 6 | Staff の既存デプロイの更新 | 「デプロイ」→「デプロイを管理」→ 既存の Web アプリのデプロイの鉛筆（編集）→ バージョン「新バージョン」→「デプロイ」。**新しいデプロイを作らない**（URL が変わり、店舗 iPad・Admin からつながらなくなる） |
| 7 | Admin のコードの反映とデプロイの更新 | Shiftly-Admin で手順 5・6 と同じ（`admin/Code.js`・`admin/admin.html`・`admin/appsscript.json`） |
| 8 | 権限の承認（変わる場合だけ） | 各エディタで `shiftlyAuthorize` を実行して承認 |
| 9 | 版の確認 | `shiftlyMaintenanceStatus` の実行ログで、コードの版が修正版になり、DB のスキーマの版が変わっていないことを確認 |
| 10 | 業務の再開 | `shiftlyMaintenanceFinish`（DB の照合の後、全員のログインを解除して再開。DB を手で変えていなければ給与は停止されない） |
| 11 | 動作の確認 | 管理者用 URL・店舗 iPad の URL が変わっていないこと、iPad で打刻（出勤・退勤）できること、管理画面の主な画面（勤怠・シフト・給与計算）が開けることを確認。店舗に再開を連絡 |

### 2.3 失敗したとき（停止・復旧の方針）

- 手順 5〜9 で失敗した・動作がおかしい場合は、**保守中のまま（業務は止めたまま。紙のタイムカード）** にして、次のとおり元の版に戻す
  - 各プロジェクトで「デプロイを管理」→ 既存のデプロイの編集 → バージョンに**手順 4 で記録した番号**を選んで「デプロイ」（URL は変わらない）。エディタのコードも元の版に戻す（元の版の配布物の `core/`・`admin/` で置き換える）
  - `shiftlyMaintenanceStatus` で元の版に戻ったことを確認してから `shiftlyMaintenanceFinish`
- 元に戻せない・原因が分からない場合は、保守中のまま開発者に連絡する（docs/incident-response.md）。推測でファイルを差し替えない・DB を変更しない
- DB は、この手順では変更しない（スキーマの版が変わらない修正版だけを反映するため）。DB を戻す必要がある場合は、docs/operations-guide.md「9」の保守作業による

### 2.4 次期以降の候補（約束しない）
- Setup による更新・ロールバック、更新に伴う DB の移行、アプリ内の復元（稼働中の DB の切替）

## 3. 障害時

- 障害の全体の流れ: docs/incident-response.md（打刻できない・データの確認・保守作業・開発者への連絡・DB のファイルの消失）
- アプリが止まった・データを戻したい: docs/operations-guide.md「3. 通信障害・システム停止時」「9. 保守作業（データの復元）」
- 「画面の世代の記録を確認できないため、データの更新を停止しています」: 保守作業（開始 → 終了）で再開する。記録を自動で作り直すことはしない（Codex 監査24 A1）
- 想定外の失敗が起きた場合は「迷ったら止める」（docs/decisions.md D-024）。推測で DB を差し替えない・上書きしない

## 4. 配布物の取り扱い（初回の構築）

- 管理者の環境が GitHub から自動でコードを取得することは**しない**（長期有効の GitHub トークンを埋め込まない・未承認の外部コードを自動実行しない）
- 配布物は開発者が `npm run build && npm run build:gas` で作成した `dist/gas/setup/`（Release.js に Core/Admin の配布物と SHA-256 を同梱）。Setup は配置前に各ファイルの SHA-256 を再計算して照合（配布経路内の破損・改ざんを検知）
