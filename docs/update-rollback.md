# アップデート・ロールバック

## 1. 配布の流れ（非公開 GitHub からの更新取得）

- 管理者の環境が GitHub から自動でコードを取得することは**しない**（長期有効の GitHub トークンを埋め込まない・未承認の外部コードを自動実行しない）
- 新バージョンは開発者が `npm run build && npm run build:gas` で作成した `dist/gas/setup/`（Release.js に Core/Admin の配布物と SHA-256 を同梱）を、管理者の Setup プロジェクトに反映する（clasp push またはファイル貼り付け）。これが「承認済みの配布物」となる
- Setup は配置前に各ファイルの SHA-256 を再計算して照合（配布経路内の破損・改ざんを検知）

## 2. 更新手順（Setup の「アップデート」）

| 段階 | 処理 | 失敗時 |
|---|---|---|
| 1. 確認 | 現在の版（Core の ping）と Setup 同梱の版を比較し、管理者が承認（営業時間外のチェック） | — |
| 2. prepare | Core: メンテナンス状態（スタッフの操作を停止）→ **更新前バックアップ**（DB の複製） | バックアップ失敗なら更新せず中止・メンテナンス解除 |
| 3. code | 配布物検証 → Staff/Admin のコードを更新（updateContent） | ロールバック |
| 4. deploy | バージョン作成 → **既存デプロイを更新**（URL は維持） | ロールバック |
| 5. migrate | Core: DB マイグレーション（列・テーブル追加は自動。既存シートの列幅・ヘッダーも拡張。**破壊的変更は承認がなければ停止**） | ロールバック（コードを戻した後、プログラムと DB の構造が一致する場合のみメンテナンス解除） |
| 6. finish | Core: 整合性確認 → アプリ版を記録 → メンテナンス解除 | **DB の移行後のため旧プログラムへ戻さず**、新しい版のままメンテナンスを継続（v1.3。Codex 監査2 #3・監査3 #1） |

- 更新中もメンテナンス状態で書き込みを止めるため、勤怠データの欠損は発生しない（スタッフ端末には「システム更新中」と表示。打刻は紙で記録し後で登録）
- 読み取り互換性: 新しい列は末尾に追加し、旧データの不足列は既定値で読む
- 進捗は Registry（`update.stage`）に保存され、中断しても状態を確認できる

## 3. ロールバック

| 対象 | 方法 | 自動 |
|---|---|---|
| GAS コード | 既存デプロイを直前のバージョン番号に戻す（Apps Script はバージョンを保持。URL 不変）。**切替の前にメンテナンスを開始**し、戻したプログラムと DB の構造が一致する場合のみ解除（v1.3） | 更新失敗時（DB の移行前）に自動。Setup の「直前のバージョンに戻す」でも可 |
| DB 構造・データ | 管理画面「バックアップ」で更新前バックアップを復元 | **自動では行わない**（更新後に記録された打刻は復元時に自動で再投入され失われない） |

- 復元時（Codex 監査1 #1・#2 で変更）: 復元前に自動バックアップ → バックアップの複製を**復元候補**として作成（稼働中の DB はまだ切り替えない）→ 打刻原本・修正・手動休憩・監査ログを **ID で突合**し、候補にない行をすべて再投入 → スタッフ・PIN/管理用パスコード・権限・端末は**現行の状態を引き継ぐ**（巻き戻さない）→ 全スタッフのセッションを失効 → 候補の整合性チェック → 合格した場合のみ稼働先を切り替え（不合格なら候補を破棄し、稼働中のデータは変更しない）
- 旧 DB は削除せず名前を変更して保持（さらに戻すことが可能）

## 4. 中断・障害時

| 状況 | 対応 |
|---|---|
| 更新が途中で止まった（メンテナンスのまま） | 管理画面「システム・更新」で DB 更新の再実行 → 更新の完了。またはメンテナンスの手動解除 |
| 更新の完了時に整合性チェックで問題が見つかった | 更新は完了せずメンテナンスを継続（Codex 監査1 #13）。内容を確認し、問題ないと判断した場合のみ「問題が見つかっても完了する」にチェックして完了（監査ログに記録）。DB のスキーマとアプリの版が一致しない場合は完了できない |
| 管理画面（Shiftly-Admin）と Core の接続を失った | Shiftly-Staff のエディタで `shiftlyResetAdminPairing` を実行 → Shiftly-Admin のエディタで `shiftlyAuthorize` を実行（Codex 監査1 #12） |
| Setup の秘密情報（更新用の接続）を失った | 管理画面で更新用接続をリセット（`system.resetSetupPairing`）→ Setup を開くと新しいペアリングコードで Staff を再配置・再デプロイ・再接続 |
| 破壊的 DB 変更の承認待ち | Setup に内容が表示される。確認のうえ承認して続行、または更新前バックアップから復元＋コードのロールバック |
| DB の移行後に更新の完了処理が失敗した（v1.3 以降） | プログラムは新しい版のままメンテナンスを継続する（旧プログラムは新しい構造の DB を正しく扱えないため）。移行の応答が失われて結果が不明な場合も、DB の実状態で判断し、確認できなければ移行済みとして扱う。管理画面「システム・更新」で原因（整合性の確認結果など）を確認・解消し、Setup を開いて「更新を再開」を押す（バックアップ・配備はやり直さず、DB 更新・完了処理から行う） |
| DB の移行後に旧版へ戻す必要がある（例: v1.3→v1.2） | 自動では行わない。①メンテナンスのまま、Google 所有者が Drive の `05_Backup` にある更新前バックアップ（旧構造）を確認 ②Setup の「直前のバージョンに戻す」でコードを旧版へ ③旧版の管理画面「バックアップ」で更新前バックアップを復元 ④旧版の管理画面で状態を確認してからメンテナンスを解除。更新後に記録された打刻は復元時に再投入されるが、新しい版でのみ扱える記録（休憩の申告・早出残業申請など）は旧版では使われないため、給与は旧版の規則で計算される点に注意 |
| プログラムと DB の構造が一致しない（v1.3 以降の Core） | Core はメンテナンスの解除を拒否する。更新を完了するか、プログラムに合うバックアップを復元する |
