# アップデート・ロールバック

## 1. 配布の流れ（非公開 GitHub からの更新取得）

- 管理者の環境が GitHub から自動でコードを取得することは**しない**（長期有効の GitHub トークンを埋め込まない・未承認の外部コードを自動実行しない）
- 新バージョンは開発者が `npm run build && npm run build:gas` で作成した `dist/gas/setup/`（Release.js に Core/Admin の配布物と SHA-256 を同梱）を、管理者の Setup プロジェクトに反映する（clasp push またはファイル貼り付け）。これが「承認済みの配布物」となる
- Setup は配置前に各ファイルの SHA-256 を再計算して照合（配布経路内の破損・改ざんを検知）

## 2. 更新手順（Setup の「アップデート」）

| 段階 | 処理 | 失敗時 |
|---|---|---|
| 1. 確認 | 現在の版（Core の ping）と Setup 同梱の版を比較し、管理者が承認（営業時間外のチェック） | — |
| 2. prepare | Setup: メンテナンスの開始を独立した要求として確定（v1.3。更新前バックアップに「メンテナンス中」を含めるため。準備を行うのは更新前の版の Core で、v1.2 の Core は準備の中の変更を複製の前に確定しない。Codex 監査7 #2）→ Core: メンテナンス状態 → **更新前バックアップ**（DB の複製） | バックアップ失敗なら更新せず中止。今回開始したメンテナンスだけを、プログラムと DB の構造の一致を確認できた場合に解除（更新の開始前からメンテナンス中だった場合・状態を確認できない場合は継続し、画面に表示。Codex 監査8 #3） |
| 3. code | 配布物検証 → Staff/Admin のコードを更新（updateContent） | ロールバック |
| 4. deploy | バージョン作成 → **既存デプロイを更新**（URL は維持） | ロールバック |
| 5. migrate | Setup: 要求の前に「移行の可能性あり」（`update.migrated`）を保存 → Core: DB マイグレーション（列・テーブル追加は自動。既存シートの列幅・ヘッダーも拡張。**破壊的変更は承認がなければ停止**） | Core が明確に拒否した場合（移行していない）のみロールバック（コードを戻した後、プログラムと DB の構造が一致する場合のみメンテナンス解除）。応答なし・通信の例外・内部エラーなど結果が不明な場合は移行済みとして扱い、**旧版へ戻さず**メンテナンスを継続（v1.3。Codex 監査5・監査6 #1） |
| 6. finish | Core: 整合性確認 → アプリ版を記録 → メンテナンス解除 | **DB の移行後のため旧プログラムへ戻さず**、新しい版のままメンテナンスを継続（v1.3。Codex 監査2 #3・監査3 #1） |

- 更新中もメンテナンス状態で書き込みを止めるため、勤怠データの欠損は発生しない（スタッフ端末には「システム更新中」と表示。打刻は紙で記録し後で登録）
- 読み取り互換性: 新しい列は末尾に追加し、旧データの不足列は既定値で読む
- 進捗は Registry（`update.stage`）に保存され、中断しても状態を確認できる

## 3. ロールバック

| 対象 | 方法 | 自動 |
|---|---|---|
| GAS コード | 既存デプロイを直前のバージョン番号に戻す（Apps Script はバージョンを保持。URL 不変）。**切替の前にメンテナンスを開始**し、戻したプログラムと DB の構造が一致し、Staff・Admin の実際のデプロイが戻し先の版の組にそろったことを確認できた場合のみ解除（v1.3）。手動の「直前のバージョンに戻す」の戻し先は、**版の組の記録**から選ぶ（Codex 監査13。各プロジェクトの「直前の版」からは推測しない）。Setup は、更新が成功するたびに正常に稼働した Staff・Admin の版の組を履歴（`pairs`）に追加し、更新中は今回配備した版の組（`update.deployed`）を記録する。①配備に着手した更新を取り消し終えていない、または実際の配備が更新の開始時の組と異なる場合は、**更新の開始時の組**へ戻す ②それ以外は、履歴で**現在の組の一つ前の組**へ戻し、履歴をその組まで切り詰める（もう一度押すとさらに前の組へ）③戻し先の組を確定できない場合（初回の構築直後、以前の Setup で記録した更新の途中など）や、配備の状態を照会できない場合は、メンテナンスを開始せずに中止する。更新の再開で配備を省略し、更新を完了してよいのは、実際の配備が今回配備した版の組と**完全に一致**する場合だけ。更新の開始前からメンテナンス中だった（または開始前の状態を確認できない）場合は、自動・手動のロールバックの後もメンテナンスを継続する。これらの組み合わせ（失敗の時点 7 種類 × 開始前のメンテナンスの有無、初回の構築直後、2 回の手動ロールバック、移行後の 2 回の手動ロールバックからの再開、旧形式の記録、開始前の状態が不明、DB の構造の不一致）は tests/integration/installer.test.ts の「状態の組み合わせ」「Codex 監査13」で、版の組の完全一致により検証している（モックの Core は常に現行のコードで動くため、旧版の Core と新しい構造の DB の組み合わせ自体は検証できない） | 更新失敗時（DB の移行前）に自動。Setup の「直前のバージョンに戻す」でも可 |
| DB 構造・データ | 管理画面「バックアップ」で更新前バックアップを復元 | **自動では行わない**（更新後に記録された打刻は復元時に自動で再投入され失われない） |

- 復元時（Codex 監査1 #1・#2 で変更）: 復元前に自動バックアップ → バックアップの複製を**復元候補**として作成（稼働中の DB はまだ切り替えない）→ 打刻原本・修正・手動休憩・監査ログを **ID で突合**し、候補にない行をすべて再投入 → スタッフ・PIN/管理用パスコード・権限・端末は**現行の状態を引き継ぐ**（巻き戻さない）→ メンテナンス・進行中の更新・アプリの版も現行を引き継ぐ（バックアップ時点の「メンテナンス解除」で打刻が再開しない。v1.3、Codex 監査6 #2）→ 給与の確定データ（給与期間・計算結果のリビジョン・明細）も現行を引き継ぐ（バックアップ後に確定・訂正・発行した給与を消さず、同じ期間を再確定させない。v1.3、Codex 監査8 #1。v1.2 の Core の復元は引き継がない）。確定済みの給与がある期間は**すべて**、復元後の給与条件（時給・手当・控除など）が確定時と異なり得るため（機械的には照合できない）、**確定・訂正・明細の発行を停止**する。管理者が時給ルール・手当・控除のそれぞれについて確定時と一致することを確認し、給与計算の画面で「復元後の確認を完了」すると解除される（監査ログには確認したことだけを定型で記録し、自由記述は残さない。Codex 監査9 #1・監査10）→ 全スタッフのセッションを失効 → 候補の整合性チェック → 合格した場合のみ稼働先を切り替え（不合格なら候補を破棄し、稼働中のデータは変更しない）
- 旧 DB は削除せず名前を変更して保持（さらに戻すことが可能）

## 4. 中断・障害時

| 状況 | 対応 |
|---|---|
| 更新が途中で止まった（メンテナンスのまま） | Setup を開いて「更新を再開」（または管理画面「システム・更新」で DB 更新の再実行 → 更新の完了）。メンテナンスを手動で解除してよいのは、更新の開始前はメンテナンス中でなかったことを確認でき、かつ管理画面「システム・更新」で DB の構造とプログラムが一致している場合だけ（v1.3 の Core は一致しない場合の解除を拒否する。Codex 監査9 #3）。Setup は準備の段階（更新前バックアップまで）の失敗では配備を操作せず、今回開始したメンテナンスだけを、現在の状態を確認できた場合に解除する。更新の開始前からメンテナンス中だった場合は、失敗・ロールバックの後もメンテナンスを継続する |
| 更新の完了時に整合性チェックで問題が見つかった | 更新は完了せずメンテナンスを継続（Codex 監査1 #13）。内容を確認し、問題ないと判断した場合のみ「問題が見つかっても完了する」にチェックして完了（監査ログに記録）。DB のスキーマとアプリの版が一致しない場合は完了できない |
| 管理画面（Shiftly-Admin）と Core の接続を失った | Shiftly-Staff のエディタで `shiftlyResetAdminPairing` を実行 → Shiftly-Admin のエディタで `shiftlyAuthorize` を実行（Codex 監査1 #12） |
| Setup の秘密情報（更新用の接続）を失った | 管理画面で更新用接続をリセット（`system.resetSetupPairing`）→ Setup を開くと新しいペアリングコードで Staff を再配置・再デプロイ・再接続 |
| 破壊的 DB 変更の承認待ち | Setup に内容が表示される。確認のうえ承認して続行、または更新前バックアップから復元＋コードのロールバック |
| DB の移行後に更新の完了処理が失敗した（v1.3 以降） | プログラムは新しい版のままメンテナンスを継続する（旧プログラムは新しい構造の DB を正しく扱えないため）。移行の応答が失われる・内部エラーなどで結果が不明な場合も、移行済みとして扱う（Core で移行が進行中の可能性があるため、DB の版の読み取りでは判断しない）。Setup の実行が移行の段階で中断した場合も同様。管理画面「システム・更新」で原因（整合性の確認結果など）を確認・解消し、Setup を開いて「更新を再開」を押す（バックアップ・配備はやり直さず、DB 更新・完了処理から行う）。移行の要求が通信の例外で終わった場合も同様（Codex 監査6 #1）。再開で配備を省略するのは、Apps Script 上の実際のデプロイがこの更新で配備した版を指す場合のみ（手動で旧版へ戻した後は、配備からやり直す。完了処理の前にも確認する。Codex 監査6 #3）。デプロイを照会できない場合（一時的な障害など）は、何も変更せずに中断する（メンテナンスは継続。時間をおいて再実行）。移行の可能性がある更新の続きでは、配備をやり直す場合も旧版へ自動では戻さず、更新前バックアップを取り直さない（最初の更新前バックアップの参照を保持。Codex 監査7 #1）。承認待ちからの再開でも、移行の前に配備を照合する |
| DB の移行後に旧版へ戻す必要がある（例: v1.3→v1.2） | **位置づけ: 緊急時に打刻を続けるための手段で、給与計算には非対応**（v1.2 のコードは変更できず、v1.3 の記録＝休憩の申告・シフト外の実労働の確認・早出残業申請を使わないため。旧版では、v1.3 で「休憩を取得しなかった」と記録した勤務にも固定休憩を控除する。例: 時給 1,200 円・09:00〜17:00・固定休憩 30 分・休憩なしの勤務は、正しくは 9,600 円だが旧版では 9,000 円。Codex 監査8 #2・監査9 #2）。自動では行わない。**戻す手順**: ①メンテナンスのまま、Google 所有者が Drive の `05_Backup` にある更新前バックアップ（旧構造）を確認 ②Setup の「直前のバージョンに戻す」でコードを旧版へ ③旧版の管理画面「バックアップ」で更新前バックアップを復元 ④旧版の管理画面で状態を確認してからメンテナンスを解除（v1.3 の Setup で行った更新の更新前バックアップは「メンテナンス中」を含むため、旧版の Core で復元してもメンテナンスは継続する。Codex 監査7 #2）。**更新前バックアップ以外（日次・手動など営業中に取得したもの）を旧版の Core で復元すると、旧版の Core はメンテナンスの状態を引き継がないため、復元と同時にメンテナンスが解除される**。旧版へ戻す場合は更新前バックアップを使う。ロールバックした時点で進行中の更新は「失敗」として終了する（移行の可能性がある更新は、次回の実行でも旧版へ自動で戻さず、最初の更新前バックアップの参照を保持したまま、配備から行う）。**給与の扱い**（旧版のコードは変更できないため、システムでは止められない。管理者が運用で守る）: ⑤**影響期間**＝v1.3 で勤務を記録した期間と、旧版で運用する期間を含む給与期間。**影響期間の給与は、旧版で確定・訂正・明細の発行をしない**（旧版の警告を「確認済み」にして確定しない）。v1.3 へ再更新した後に v1.3 で計算・確定するか、⑦の記録から別に計算する ⑥旧版へ戻すと決めた時点から v1.3 へ再更新するまでの勤務は、**紙のタイムカードと並行して記録**する。紙には出勤・退勤に加え、休憩の取得状況（予定どおり・取れなかった・実際の時刻）と、シフト外の勤務の有無・実労働かどうか（管理者の確認）を記入する ⑦v1.3 の記録の参照元: 復元で切り替える前の v1.3 の DB は削除されず、Drive の `01_Database` に `Shiftly Database (replaced 日時)` の名前で残る（v1.2・v1.3 とも）。v1.3 で記録した休憩の申告・シフト外の実労働の確認・早出残業申請・給与条件・確定結果は、このスプレッドシートで確認できる。v1.3 時点のバックアップ（`05_Backup`）も参照元になる。v1.3 が起動しない場合も、これらのファイルは Google 所有者が Drive で直接開ける ⑧旧版での復元は確定済みの給与を引き継がない（旧版の動作）。復元前に確定済みだった期間は、旧版で再確定しない（確定結果は ⑦の旧 DB で確認する）。影響期間の確定状況は、v1.3 へ再更新して照合を終えるまで、管理者が別に記録・管理する。**v1.3 へ再更新した後、影響期間を確定する前の照合・再登録**（Codex 監査10。システムでは自動で行わない）: ⑨Setup で v1.3 へ再更新する。再更新で移行されるのは旧版で稼働していた DB のため、v1.3 の旧 DB にだけある記録（休憩の申告・シフト外の実労働の確認・早出残業申請・確定済みの給与・復元後の確認の状態）は**含まれない** ⑩**確定済みの給与の照合（二重確定の防止）**: 旧 DB の `payroll_results` シートで、影響期間の確定結果（期間・スタッフ・リビジョン・支給額・状態）を一覧にし、再更新後の DB の確定結果と照合する。旧 DB で確定済みの期間・スタッフは、**再更新後の DB で確定しない**（明細・支払いは旧 DB の確定結果を正とする）。この一覧は ⑧の確定状況の記録とあわせて保管する ⑪**未確定の期間の再登録**: 旧 DB と紙の記録（⑥）を見比べ、影響期間の各勤務について再登録する（画面は v1.3 のもの。Codex 監査11 #2）。(a) **休憩の取得状況**: 管理画面には休憩の申告を新規に登録する画面がないため、**スタッフ本人が Staff 画面から申告し直す**（本人確認済み＝PIN 設定済みのスタッフは「自分の勤怠（確認・修正）」、PIN | プログラムと DB の構造が一致しない（v1.3 以降の Core） | Core はメンテナンスの解除を拒否する。更新を完了するか、プログラムに合うバックアップを復元する |
