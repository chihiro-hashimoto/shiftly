# 運用ガイド（管理者向け）

## 1. 日々の運用

通常は店舗 iPad 1 台で運用します。管理者は Staff 画面右上の「管理者ページ」から管理者パスワードで管理者モードに入ります（5 分間操作がないと自動でスタッフ画面に戻ります。終わったら「ログアウト」）。PC の Shiftly-Admin（Google 所有者）からも同じ操作ができます。

| 作業 | 画面 |
|---|---|
| 勤務状況・要対応の確認 | 管理画面「ダッシュボード」（要確認の申請・勤怠の件数） |
| 早出・残業申請の承認／シフト外の勤務の確認／本人修正・休憩申告の確認 | 「申請・確認」。**申請がなくても実際に働いた時間は「実労働として登録」**してください。準備・片付け・待機など指揮命令下の時間は労働時間です。「実労働なし」は本人に確認したうえで登録します |
| 打刻漏れの修正（理由必須。原本は残る） | 「勤怠」→ スタッフの「明細・修正」。スタッフ本人も「勤怠確認・修正」から修正できます（PIN 未設定のスタッフの申告は承認が必要） |
| 時給ルール・月給設定 | 「スタッフ・権限」→ 各スタッフの「時給ルール」／「月給設定」 |
| シフト作成 → 公開 | 「シフト」 |
| 通知の確認（打刻漏れ・休憩不足・欠勤・有給期限・給与未確定・容量不足・バックアップ失敗） | 「通知」（毎日 4 時台に自動検出） |

## 2. 月次の給与

1. 「給与計算」で対象月の期間を作成 → 仮計算
2. 打刻漏れ・未処理の修正・**未確認のシフト外の時間・未処理の早出残業申請**を解消（確定できない理由が一覧表示される）。給与はシフトを基準に計算し、シフト外の時間は実労働と確認したものだけを加えます。予定休憩は「取得した」と確認されたものだけを差し引きます
3. 控除（所得税・住民税・社会保険料等）を入力。控除がない場合は「控除なし」を明示
4. 欠勤・遅刻早退の控除は、給与規定に基づき管理者が承認した分のみ「調整」に登録（シフトからは自動控除しない）
5. 確認項目（休憩不足など）を確認 → 確定
6. 明細発行 → 管理者端末で印刷（紙で交付）。電子交付は本人の承諾がある場合のみ
7. 誤りがあれば「訂正」（理由必須。新しい版が作られ、旧版は保持）

**本番利用前に、少なくとも 1 給与計算期間は紙のタイムカード・従来の計算と並行運用し、全員分を照合してください。**

## 3. 通信障害・システム停止時（代替手段）

- 店舗 iPad が「オフライン」表示の間は**紙のタイムカード**に記録
- 復旧後、管理画面「勤怠」→「紙のタイムカードから登録」で理由付きで登録

## 3.5 管理者パスワードと PIN

- 管理者パスワードの初期設定・忘れたときの再設定は、Google 所有者が PC の管理画面（Shiftly-Admin）「システム・保守」で行います。再設定すると、すべての管理者モードが終了します
- 管理者パスワードは管理者本人以外に教えないでください。iPad で入力するときは周囲から見えないようにし、使い終わったら必ず「ログアウト」してください
- 重要な操作（給与確定・権限変更・PIN の設定など）の前には、もう一度パスワードの入力を求められます
- **データの復元は安全性確保のため、Google所有者による保守作業として行います。**アプリ（管理画面・店舗 iPad）には復元のボタンはありません（v1.3。D-027）。手順は「9. 保守作業（データの復元）」
- 保守作業の後は、保守作業の前に開いていた画面（Google 所有者の管理画面・店舗 iPad のスタッフ画面と管理者モード）からは、業務の更新（設定・スタッフ・給与条件・シフト・勤怠・申請・給与計算など）を保存できません。「画面を読み込み直してください」と表示されたら「読み込み直す」を押し、最新の内容を確認してから入力し直してください（入力中の内容は保存されていません。D-026）。保守作業の終了で全員のログインが解除されるため、ログインし直してください
- スタッフの PIN は任意です。PIN のないスタッフは名前の選択だけで出退勤できますが、給与・給与明細・勤怠の詳細は表示されません。本人確認のうえ PIN を設定することを推奨します（6 桁以上を推奨）
- 給与明細・CSV・Excel のファイルは共用 iPad には保存されず、Google 所有者の Drive に保存されます。iPad で画面を印刷・保存しないでください（アプリは端末に保存されたファイルを削除できません）

## 4. 端末

- 新しい iPad・Safari のデータ消去後: 「店舗端末」で登録コードを発行して再登録
- 紛失・トークン漏えいの疑い: 該当端末を「失効」→ 必要なら新しく登録
- 管理者の Google アカウントで店舗 iPad にログインしない

## 5. バックアップ

- 自動: 日次（直近 30 世代）・月次（直近 12 世代）。手動: 管理画面「バックアップ」の「今すぐバックアップ」、保守作業の開始時。Drive の `Shiftly/05_Backup`。失敗した場合は通知（重要）が出ます
- 「更新前」のバックアップは以前の版の自動更新で作られたものです（v1.3 では自動更新を行わないため、新しくは作られません）
- 記録の原本（勤怠・給与・明細）は DB と Drive に保持され、法定保存期間（5 年、経過措置 3 年）未満の自動削除は行わない。世代管理で削除するのはバックアップの複製のみ
- **アカウント喪失への備え（管理者の判断で実施）**: 同じ Google アカウント内のバックアップだけでは、アカウント喪失・停止時に失われます。月 1 回程度、次のいずれかを推奨します
  1. 管理画面「データ出力」で勤怠・給与（Excel）・賃金台帳を出力し、暗号化した外部媒体または別の管理用アカウントに保管
  2. Drive の `Shiftly/05_Backup` の最新月次バックアップを、別の管理用 Google アカウントに共有せず**コピー**して保管（共有設定は使わない）
  - 外部・別アカウントへの転送は Shiftly が自動で行うことはありません

## 6. 容量

- Google Drive の 15GB は Gmail・Google フォトと共有。通知「Drive の空き容量が少ない」が出たら不要なメール・写真を整理するか、Google One 等の有料プランを**管理者の判断で**検討（Shiftly が自動で課金することはない）
- 容量不足時は保存・バックアップが失敗するため、紙のタイムカードで代替し、容量確保後に登録

## 7. 管理者交代

1. 新管理者の Google アカウントで Setup を実行して新環境を作成（既存環境とは別）
2. 旧環境の「データ出力」と最新バックアップを新管理者に引き継ぎ（データ移行手順は個別対応。**未実装の自動移行機能はない**）
3. 旧環境の端末を失効

## 8. 退職者

- 「スタッフ・権限」で退職処理（無効化）。勤怠・給与・監査ログは保持され、賃金台帳に残る

## 9. 保守作業（データの復元）— Google 所有者だけ

v1.3 は「正常時は自動・異常時は手動」です（D-027）。アプリ内の自動復元・稼働中の DB の自動切替は行いません。誤った操作・障害でデータを戻す必要がある場合は、Google 所有者が次の手順で、稼働中の DB（Google ドライブの `Shiftly/01_Database` のスプレッドシート）を直接直します。**稼働中のアプリの裏で DB のファイル（スプレッドシートの ID）を差し替えたり、既存の DB を上書き・削除したりしないでください。**

アプリが保証すること（サーバー側）: 開始から終了まで、Google 所有者・定期処理を含む全員の業務データの更新を止める（例外: 保守の開始・終了、初期化（shiftlyAuthorize）、読み取りに伴う監査ログの追記）／開始時のバックアップと内容の記録を作る／終了の時に、開始時にあった守る記録（打刻原本・修正の履歴・申請・確定した給与・明細・有給・スタッフ・認証・端末・監査ログ・出力とバックアップの履歴）の削除・変更、同じ ID の行の重複、行のシートの年月の不一致、数値の列の数値でない値、未完了の書き込み処理の記録、DB の整合性の問題（参照・重複・スキーマ版）を検出したら再開しない／DB のセルに数式があれば再開しない（Sheets API で「数式」と「値」を読み比べて確認。D-027 追補）／内容に変更があれば、確定済みの給与がある期間を停止する（「復元後の給与の確認」で全項目を照合し、差がない場合だけ解除）／全員のログインを解除し、保守作業の前に開いた画面からの保存を拒否する／開始時の記録を確認できない場合は、今の DB を新しい基準にして開始し直さず、保守中のまま止める（D-027 追補）。
アプリが保証しないこと（所有者の判断）: 手で直した内容が正しいこと（バックアップのどの内容に戻すかの判断）。シートの 1 行目の列名・列の順（入力の表で列を入れ替えた場合は「内容の変更」として再開し、給与は停止される）。**数式**の検出の限界（業務の DB は値だけを保存する方針で、写すときは必ず「値のみ貼り付け」にする。終了時の確認は、計算結果が数式の文字列と同じになる特殊な数式を見分けられない。Google 実環境では未検証のため、本番導入前に L24 で確認し、それまでは所有者が目視でも確認する）。照合しない内部の表（operation_journal・request_idempotency・sessions・admin_sessions・notifications・system_metadata の大部分）は手で触らない。

| # | 手順 | 方法 |
|---|---|---|
| 1 | 店舗への作業の通知 | 作業の開始・終了の予定時刻と、作業中は打刻できないことを店舗に伝える |
| 2 | 業務の更新の停止 | Shiftly-Staff のスクリプトエディタで **shiftlyMaintenanceBegin** を実行（以後、全員の更新が止まる。管理画面「システム・保守」に「保守作業中」と表示） |
| 3 | 定期処理の停止と、実行中の処理の終了の確認 | 手順 2 は、実行中の更新の処理が終わるのを待ってから開始する（スクリプトロック）。日次の定期処理は保守中は何も更新しない。実行ログ（Apps Script の「実行数」）で、開始の後に終わっていない処理がないことを確認する |
| 4 | 紙のタイムカードへの切替 | 店舗に紙のタイムカードで記録するよう連絡する（保守作業の後に「紙のタイムカードから登録」で入力） |
| 5 | 現行の環境の追加のバックアップ | 手順 2 で自動で作成される（「バックアップ」の一覧に「保守作業の開始時のバックアップ」）。失敗した場合は保守中のまま止まるので、空き容量を確保して手順 2 を再実行 |
| 6 | 復元の候補の作成 | `Shiftly/05_Backup` から戻したい時点のバックアップを選び、**閲覧用に開く**（コピーを作る場合は `05_Backup` の外に作らず、作業後にゴミ箱へ）。稼働中の DB には切り替えない |
| 7 | 候補の DB の構造・内容の確認 | 候補のシート名・1 行目の列名が稼働中の DB と同じであること、戻したい行（ID）があることを確認する。構造が違う（別の版のバックアップ）場合は戻さず、開発者に連絡する |
| 8 | バックアップの後の打刻・修正履歴・申請・確定給与などの保護と照合 | 稼働中の DB の守る記録（打刻原本 `attendance_events`、修正の履歴、申請、確定した給与 `payroll_results`・明細、監査ログなど）は**削除・変更しない**。戻すのは、失われた行の**追加**と、業務の入力・設定（シフト・給与条件・控除など）の修正だけ。どの行を戻すかを、ID で候補と照合して決める |
| 9 | 安全を確認した後の復元 | 稼働中の DB のスプレッドシートで、手順 8 で決めた行だけを候補から写す（行全体を、列の順のまま、**「値のみ貼り付け」**（編集 → 特殊貼り付け → 値のみ貼り付け））。セルに数式を入力しない。シートの削除・並べ替え・列の追加はしない |
| 10 | 既存のセッション・古い編集画面の無効化 | Shiftly-Staff のエディタで **shiftlyMaintenanceFinish** を実行。開始時の記録と照合し、問題がなければ全員のログインを解除し、画面の世代を新しくして業務を再開する。守る記録の削除・変更・DB の構造の問題・数式のセルがあれば**再開しない**（実行ログの内容に従って元に戻し、再実行する。自動では直さない） |
| 11 | 給与計算・確定給与・明細の整合の確認 | 内容に変更があった場合、確定済みの給与がある期間は停止される。管理画面「給与計算」の「復元後の給与の確認」で、確定時と現在の計算結果を全項目で照合し、差がなければ解除する。差がある場合（例: 失われた打刻を戻して確定時より勤務時間が増えた）、**その期間は停止したままにする**（アプリに強制解除・特別な確定・差額の自動支給の機能はない）。給与条件を確定時に合わせられる場合だけ、合わせてから解除する。実際の給与に訂正が必要な場合は「9.1 停止中の給与期間の例外的な手動訂正」による。整合性チェックも実行する |
| 12 | 管理者による再開の判断 | 管理者が勤怠・シフト・給与の画面で内容を確認し、店舗に再開を連絡する。紙のタイムカードの記録を「紙のタイムカードから登録」で入力する |

- 状態の確認: エディタで **shiftlyMaintenanceStatus**（保守作業中か、開始時刻、画面の世代の記録があるか）
- 開始が途中で止まった場合: 開始時の記録（00_System の `Shiftly_maintenance_snapshot_…`）を作れなかった場合は、**保守作業は開始していません**（業務はそのまま。DB を手で変更せず、時間をおいて **shiftlyMaintenanceBegin** を再実行）。開始時のバックアップだけが失敗した場合は、保守中のまま止まるので、空き容量を確保して **shiftlyMaintenanceBegin** を再実行（開始時の記録はそのまま使う。開始の後に DB を変更していると、バックアップを作り直さずに止まる）
- 開始時の記録を読み込めない場合（終了が「読み込めない」で止まる）: 一時的な失敗の可能性があるため、**記録を作り直さず**、時間をおいて shiftlyMaintenanceFinish を再実行する。記録のファイルをゴミ箱に移した場合は、ゴミ箱から元に戻してから再実行する。それでも読めない場合・保守の記録（Script Properties）が壊れた場合は「9.2」による（**開始し直す関数はありません**。v1.3 の途中の版にあった shiftlyMaintenanceRestart は D-027 追補で廃止）
- 手作業で、セルに数式を入れる・同じ ID の行を増やす・行を別の月のシート（`attendance_events__2026_11` など）へ移す・シートの名前を変える・月のシートを削除する・守る表のシートを削除する操作はしない（終了時に検出して再開しない）。入力の表（シフト・給与条件・控除など）のシートを削除した場合は「内容の変更」として再開し、確定済みの給与は停止されるが、内容が失われるので行わない
- 照合の対象は DB の行だけです。Google ドライブのファイル（明細の PDF・出力・バックアップ）は照合しないため、保守作業でこれらのファイルを削除・移動しないでください
- 「画面の世代の記録を確認できないため、データの更新を停止しています」（EPOCH_UNAVAILABLE）と表示された場合も、手順 1〜4・10〜12 の保守作業で再開する（記録を時刻などから自動で作り直すことはしない。Codex 監査24 A1）
- **この手順で安全に戻せない場合（未解決として扱う）**: 「9.2」による
- この手順は Google 実環境では未検証です（docs/live-verification.md）

### 9.1 停止中の給与期間の例外的な手動訂正（D-027 追補）

保守作業の後の「復元後の給与の確認」で差が残る期間は、**停止したままにします**（停止を外す・特別に確定し直す・差額を自動で支給する機能は v1.3 にはなく、追加しません）。通常の給与の訂正の機能は、停止していない期間ではそのまま使えます。停止中の期間の実際の給与に訂正が必要な場合だけ、管理者が**アプリの外で**次のとおり例外的に手動で訂正します。

- **アプリの記録は変えない**: 元の確定給与・明細・修正の履歴・監査ログを、スプレッドシートでの手作業を含めて変更・削除しない。停止も外さない
- **旧明細を正しい支払額として扱わない**: アプリの確定記録と実際の支払額が異なる期間の旧明細は、現在の正しい支払額を示すものとして使わない（本人に渡す場合は、訂正明細を併せて渡し、どちらが正しいかを明記する）
- **支払期日を守る**: 停止を理由に、法令（労働基準法第 24 条の賃金の支払いの原則など）・就業規則・労働契約の支払期日を超えて支払いを保留しない。不足額は次月への繰越を前提とせず、速やかに支払う。過払い額を翌月の給与から自動で差し引かない（精算の方法は本人と取り決め、必要に応じて社会保険労務士等の専門家に確認する）
- **訂正の記録**（1 件ごとに作り、アクセスを制限した場所に保存する。例: 管理者だけが閲覧できる Google ドライブのフォルダ。Shiftly のフォルダ・DB の中には置かない）:

| 項目 | 内容 |
|---|---|
| 対象 | スタッフ（ID と氏名）・給与期間 |
| 当初の確定給与 | アプリの確定時の総支給額・控除・差引支給額（「復元後の給与の確認」の確定時の値） |
| 訂正後の給与と計算根拠 | 訂正後の各金額と、勤務時間・時給・手当などの根拠（紙のタイムカード・戻した打刻など） |
| 控除等への影響 | 社会保険料・所得税・住民税・その他の控除への影響と、その扱い |
| 差額 | 不足（追加で支払う）または過払い（精算の方法を本人と取り決める）の金額 |
| 訂正理由 | 保守作業の内容（日時・戻した記録）と、差が生じた理由 |
| 支払日・支払記録 | 差額を支払った日・方法・振込記録など |
| 訂正明細・賃金台帳 | 本人に渡した訂正明細の控え。賃金台帳（労働基準法第 108 条）への反映の記録 |
| 二重支払・二重計上の防止 | 差額を支払済みであることの記録。後日アプリで同じ期間を訂正できるようになっても、差額を重ねて支払わない・計上しないための照合欄 |
| 開発者への依頼 | アプリ内の記録の整合（停止中の期間の扱い）を開発者に依頼した日と内容 |

- **対象外の期間への影響の確認**: 訂正の対象の期間以外（停止していない期間・新しい期間）の給与計算・確定が、通常どおり行えることを確認する（停止は確定済みの期間ごとで、未確定の期間は通常どおり計算・確定できる。tests/integration/maintenance.test.ts で確認済み。Google 実環境では未検証）
- アプリ内で停止中の期間を訂正・再照合する機能は、将来の改善の候補です（v1.3 では提供しません）

### 9.2 開始時の記録・保守の記録・DB のファイルを失った場合（D-027 追補）

- **今の DB を新しい正常な状態とみなして保守を開始し直す処理は提供しません**。所有者の確認だけで、データの完全性を保証したことにはしません。安全な状態を確認できるまで保守を終了しません（業務の更新は止めたまま）
- 一時的な読み取りの失敗（記録のファイルを読めない）の場合: 記録を作り直さず、時間をおいて再実行する（「9」の「開始時の記録を読み込めない場合」）
- 開始時の記録・保守の記録（Script Properties の `SHIFTLY_MAINTENANCE`）を本当に失った場合: 店舗は**紙のタイムカードで運用**し、**開発者に個別の復旧を依頼**する。Script Properties の値を手で消す・書き換える・別のファイルを記録として置く、などで保守を終わらせない
- DB のスプレッドシート自体を失った・開けない場合、守る記録自体が壊れている場合、別の版のバックアップから戻す必要がある場合も同じです（v1.3 には稼働中の DB を切り替える手順・機能はありません。推測で DB を差し替えない）
- 開発者による個別の復旧は、v1.3 のアプリの機能ではなく、手順と能力は**未検証**です（保証しません）。本番導入の前に、少なくとも、開発者の個別対応の手順書と、バックアップ（`05_Backup` の複製）から業務の記録を取り出せることを、検証用の環境で確認します（docs/live-verification.md の L25）
