### マージを止める指摘

1. **高 — 移行中の通信例外で、旧 Core がスキーマ v2 の DB に接続する。** v1→v2 の移行リクエストを送信した後、Core の処理が続いている間に Setup の `UrlFetchApp.fetch` が例外を投げると、`migrated` は `false` のままです。期待は新 Core を維持することですが、実装はロールバックに進みます。メンテナンス開始のロック取得までに移行が確定すると、旧 Core と v2 DB の組み合わせになり、旧管理画面ではスキーマ不一致を検査せず手動解除できます。店舗全体の勤怠・給与処理に影響します。移行呼び出しの直前に結果不明の状態を永続化し、例外でも新 Core を維持してください。通信例外を投げる回帰テストも必要です。既存テストは失敗応答を返す経路を検証しています。実機の通信障害は未検証です。 [setup.ts](../../src/gas/setup.ts:42) · [installer.ts](../../src/setup/installer.ts:524) · [installer.test.ts](../../tests/integration/installer.test.ts:150)

2. **高 — 更新前バックアップを復元すると、確認前に打刻が再開する。** 営業中の状態から更新を準備すると、メンテナンス設定は書き込み待ちのまま DB が複製されます。そのバックアップをメンテナンス中に復元すると、候補が保持する `off` がそのまま有効になります。メモリ上の Core で復元前 `true`、復元直後 `false` を確認しました。手順書は、復元後に Google 所有者が状態を確認してから解除するとしています。店舗全体で確認前に打刻を受け付けるため、復元候補に現行のメンテナンス状態を引き継いでから切り替え、旧版に戻す手順も含めて検証してください。 [update.ts](../../src/backend/handlers/update.ts:24) · [ops.ts](../../src/backend/handlers/ops.ts:543) · [update-rollback.md](../../docs/update-rollback.md:44)

4. **中 — 前日の退勤漏れがあると、当日の休憩申告が前日の勤務に付く。** 前日09:00に出勤して退勤を忘れ、翌日09:00に出勤し17:00に退勤します。予定休憩は前日60分、当日30分、時給は1,200円です。当日の30分を取得した場合、当日分は450分・基本給9,000円が期待値です。メモリ上では前日の60分が表示され、そのまま確認すると退勤は成功しますが、当日分の仮計算は480分・9,600円でした。前日の未退勤が残る間は給与確定も止まります。退勤前の表示・打刻・休憩保存で、退勤漏れを考慮した同じ勤務キーを使ってください。 [requests.ts](../../src/backend/handlers/requests.ts:178) · [requests.ts](../../src/backend/handlers/requests.ts:476) · [attendance.ts](../../src/backend/handlers/attendance.ts:67)
